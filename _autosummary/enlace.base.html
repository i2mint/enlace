enlace.base¶

Core data structures for enlace platform configuration.

enlace does not enforce access — that’s enlace_auth’s job. But enlace does read AppConfig.access and AppConfig.allowed_users for one narrow purpose: filtering the /_apps listing so authenticated users don’t see entries they couldn’t open anyway. That makes the access string vocabulary part of enlace’s contract — the values "public" | "local" | "protected:shared" | "protected:user" are the ones enlace.access.can_see_app understands; anything else is treated as deny-by-default.

The fields are otherwise opaque to enlace: enforcement, session lookup, allowlist matching at request time, and CSRF all live in the enlace_auth plugin (passed in via build_backend(..., plugins=[...])).

Likewise, [auth.*] and [stores.*] tables in platform.toml are preserved as untyped dicts on PlatformConfig so plugins can deserialize them with their own models.

Any other top-level table is not read by enlace. from_toml logs a warning for each one (a misnested [oauth_server] or a typo such as [stores_] would otherwise vanish), unless [platform] foreign_tables declares it as owned by another tool, and enlace doctor reports the same list.

Resolved configuration for a single discovered app.

extra="allow" lets plugin strategies (e.g. enlace_docker) carry their own typed fields — dockerfile, image, compose_file, service, etc. — without enlace having to enumerate them. The plugin’s BackendStrategy reads them via attribute access (app.dockerfile); enlace itself ignores them.

forward_platform_credentials: bool¶

Forward the visitor’s platform session and CSRF credentials (cookies and the X-CSRF-Token header) to the process. Off by default: a process app is a separate program with its own dependencies, and bearer-token apps such as MCP connectors never need them. Response filtering (no platform Set-Cookie, Clear-Site-Data or Service-Worker-Allowed) applies either way.

class enlace.base.AppImportError(**data)[source]¶

Bases: BaseModel

Why an app could not be loaded, recorded instead of raised.

Recorded at discovery (on_import_error="record" — see enlace.discover.discover_apps()) or at compose time, when enlace.compose.build_backend() contains a per-app load failure and mounts a 500 stub in the app’s place (see enlace.degraded and misc/docs/decisions/0001-loud-and-local-app-load-failures.md).

Importing a module runs arbitrary module-level code, so exception_type is not necessarily an ImportError: the failure seen in production was a PermissionError from a dependency reading a root-only dotenv at import.

The exception object itself is kept privately (exception) so a caller that must refuse to boot can re-raise it with its real traceback. It is never serialized.

class enlace.base.BuildConfig(**data)[source]¶

Bases: BaseModel

Declarative build instructions for an app’s compiled frontend.

Mirrors the [build] table in app.toml. It describes the app, not its deployment — a Vite/Next/esbuild app has a build command whether or not enlace serves it — so it keeps the “apps don’t know about enlace” principle intact. enlace (or any deployer) runs these as an explicit step via enlace build; enlace never builds at request time.

install / build accept either a single string (split with shlex) or a list of argv tokens. cwd is resolved relative to the app directory at discovery time; None means “the app directory”. env_vars is a hint of which env vars the build honours (e.g. VITE_API_BASE) so deployers know what they may inject — enlace does not choose values. outputs is an optional hint of produced paths.

enlace.base.CONTAINED_LOAD_ERRORS: tuple[type[BaseException], ...] = (<class 'Exception'>, <class 'SystemExit'>)¶

What a contained app-load failure may be. Importing a module runs arbitrary module-level code, so the net is Exception, not ImportError — plus SystemExit, because a module that calls sys.exit() at import is a broken app, and under a pre-forking server an uncaught one ends the worker and with it every other app. KeyboardInterrupt is not caught: Ctrl-C must still stop a dev server mid-boot.

classmethod from_toml(path=PosixPath('platform.toml'))[source]¶

Load configuration from a TOML file, falling back to defaults.

Relative apps_dirs / app_dirs / shared_assets_dir entries in the TOML are resolved against the TOML file’s own directory, not the process working directory. This makes a platform config host-portable: the same file works wherever the repo is checked out, as long as sibling app repos keep their relative layout. Absolute (and ~-prefixed) paths are left untouched.

Reads environment variables as overrides (applied after relative resolution, so env values are taken verbatim — host-specific by design):

  • ENLACE_APPS_DIRS (pathsep-delimited): container directories

  • ENLACE_APP_DIRS (pathsep-delimited): individual app directories

  • ENLACE_APPS_DIR (legacy): single container directory

Top-level tables enlace does not read are logged as warnings (and kept on unknown_tables) unless [platform] foreign_tables lists them; they are never an error, since a platform.toml may carry tables for other tools.

Parameters:

path (Path) – Path to platform.toml. If the file doesn’t exist, returns a PlatformConfig with all default values.

Return type:

PlatformConfig

enlace.base.unknown_toml_tables(data, *, foreign_tables=())[source]¶

Top-level keys of a parsed platform.toml that nobody claims, as messages.

A key is claimed when enlace reads it (ENLACE_TABLES) or when the config declares it in foreign_tables. Each message names the key and, when one is close, the enlace table it was probably meant to be.

Return type:

list[str]

>>> unknown_toml_tables({"platform": {}, "deploy": {}, "stores_": {}},
...                     foreign_tables=["deploy"])
['[stores_] is not an enlace table and is ignored (did you mean [stores]?)']
