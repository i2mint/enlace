enlace.ratelimit¶

Opt-in, per-app, per-client rate limits for mounted apps.

An app declares limits in its app.toml; enlace enforces them in front of the app, so the app needs no code (and still runs alone without them):

[rate_limit]
"POST /attempts" = "60/minute"      # method + path under the app's API prefix
"/search" = "10/second"             # no method: any method
"POST /items/*" = "100/hour"        # fnmatch-style glob

A request over its limit gets 429 Too Many Requests with Retry-After.

Who the client is. Behind a reverse proxy the TCP peer is the proxy, so the client address comes from X-Forwarded-For – but only when the peer is one of platform.toml’s [platform] trusted_proxies, and read right to left skipping trusted hops, so a client cannot spoof it by sending the header itself. With no trusted_proxies the peer address in the ASGI scope is used as is (which is already the client when the server itself resolves proxy headers, as uvicorn does for a loopback proxy by default). IPv6 clients share a bucket per /64. Behind a proxy on a unix socket (uvicorn --uds) there is no peer address at all: pass trust_unix_socket=True (platform.toml [platform] trust_unix_socket = true) so the proxy’s header is read; otherwise every client shares one “unknown” bucket.

What is matched. The request path is normalised first (//, . and .. collapsed, as an upstream would resolve them), so a rule cannot be sidestepped with /a/../attempts. A GET rule also covers HEAD. CORS preflights (OPTIONS with Access-Control-Request-Method) are never counted. A websocket handshake is matched as GET and refused with close code 1008.

Scope of the guarantee. Buckets are in memory, per process: a host running N worker processes allows up to N times the declared rate. Each rule tracks at most max_keys clients. When full, idle buckets (full again, or with no hit left in the window) are dropped first, since they carry no information; only then is the least recently seen evicted (on_overflow="evict", the default, warned once), and an evicted bucket comes back full, so a client rotating through more addresses than that (e.g. many IPv6 /64s) is not held to the rate. on_overflow="deny" refuses new clients instead (fail closed). It bounds abuse; it is not an exact quota. The limiter is a seam (make_limiter) for a shared one.

**In production behind a proxy, set ``trusted_proxies``** unless the server already resolves the client from the proxy’s header: otherwise every client shares the proxy’s address, and one abusive client exhausts everyone’s bucket.

Reusable on its own. The client-address and limiter halves import nothing beyond the standard library, so other services use them directly (heed’s public ingest endpoint does): client_address() + bucket_key() say who the client is, and any Limiter – TokenBucketLimiter, SlidingWindowLimiter, or RedisLimiter (one count shared by every worker and host; needs the [redis] extra) – says whether it may proceed. To share enlace’s own limits across workers, pass the Redis one to the seam:

RateLimitMiddleware(app, rules=rules, make_limiter=lambda rate: RedisLimiter(
    client, rate))

Each rule charges its own key (the rule’s RateLimitRule.id plus the client), so one shared client never mixes two rules’ counts.

Pure ASGI middleware enforcing RateLimitRule s per client.

Every rule a request matches is charged (a request may count against a narrow and a broad rule); the first one exhausted answers 429.

trust_unix_socket trusts a connection with no peer address (a proxy on a unix socket) to name the client in X-Forwarded-For; anything that can reach the socket can then pick its own address, so only the proxy should.

class enlace.ratelimit.RedisLimiter(client, rate, *, namespace='enlace:rl', fallback=None, max_keys=100000, retry_seconds=5.0, on_error='fallback', clock=<built-in function time>)[source]¶

Bases: _AllowMixin

Fixed window in Redis: one count per key per window, shared by every worker.

client is any redis-py compatible client (injected; tests use a fake), or build one with from_url(); an asyncio client is refused up front (the limiter’s calls are synchronous). When Redis errors, on_error decides: "fallback" (the default) asks fallback (a per-process in-memory limiter by default), so an outage degrades protection instead of either refusing everything or lifting the limit; "deny" refuses every request (fail closed, for a public endpoint that would rather refuse than allow N workers times the rate) and "allow" admits every one (fail open).

A fixed window admits up to twice rate.limit across a window boundary; the price of one round trip and one counter per key. Keys go into Redis as given, so they must come from a bounded set (client bucket keys, rule ids), never raw client input. After an error on_error alone decides for retry_seconds (one warning per outage), so a hung Redis costs one socket_timeout per interval rather than one per request. max_keys sizes the default fallback only.

acquire does blocking I/O: RateLimitMiddleware runs a limiter whose blocking attribute is true in a worker thread, off the event loop.

class enlace.ratelimit.SlidingWindowLimiter(rate, *, max_keys=100000, on_overflow='evict', min_sweep_seconds=1.0, sweep_batch=1024, clock=<built-in function monotonic>)[source]¶

Bases: _BoundedKeys, _AllowMixin

In-memory sliding window: at most rate.limit requests in any window.

Unlike TokenBucketLimiter there is no refill between hits: a client that spent its budget waits until its oldest hit leaves the window. Per process (N workers allow N times the rate); the number of tracked keys is bounded (max_keys: keys with no hit left in the window go first, then on_overflow decides) so a flood of distinct keys cannot exhaust memory. Each key keeps up to rate.limit timestamps, so memory is bounded by max_keys * rate.limit: prefer TokenBucketLimiter (one pair of floats per key) for large limits.

>>> now = [0.0]
>>> lim = SlidingWindowLimiter(Rate(1, 10), clock=lambda: now[0])
>>> lim.acquire("a"), lim.acquire("a")
(0.0, 10.0)
>>> now[0] = 10.0
>>> lim.allow("a")
True
class enlace.ratelimit.TokenBucketLimiter(rate, *, max_keys=100000, on_overflow='evict', min_sweep_seconds=1.0, sweep_batch=1024, clock=<built-in function monotonic>)[source]¶

Bases: _BoundedKeys, _AllowMixin

In-memory token buckets, one per key, bounded in number (LRU eviction).

A bucket holds up to rate.limit tokens and refills continuously at limit / window per second, so bursts up to the limit pass and the sustained rate is the declared one. At max_keys keys, full buckets are dropped first, then on_overflow decides (see _BoundedKeys).

>>> now = [0.0]
>>> lim = TokenBucketLimiter(Rate(1, 10), max_keys=1, on_overflow="deny",
...     clock=lambda: now[0])
>>> lim.acquire("a"), lim.acquire("b")  # "a" is busy: the new "b" is refused
(0.0, 10.0)
>>> now[0] = 10.0  # "a" is full again: idle, so it makes room
>>> lim.allow("b")
True
